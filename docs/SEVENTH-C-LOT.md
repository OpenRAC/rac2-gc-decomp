# Seventh RAC2 C lot - the call family opens

The previous lot put one body in the boot that counts once, because the level catalogues
are built with an empty external map. This lot is the opposite trade: **one body that calls
another function**, placed in all twenty-seven overlays, and it pays twenty-eight-fold.

| | Before | After |
| --- | ---: | ---: |
| Boot | 93 functions / 2 028 bytes | **94 / 2 056** |
| Levels | 2 091 placements / 48 156 bytes | **2 183 / 49 832** |
| Total | 50 184 bytes (0.1029 %) | **51 888 bytes (0.1064 %)** |

`FUN_0034F3B8` is the whole lot: twenty-eight bytes, `addiu sp, sp, -0x10; sd ra, 0(x);
jal; li a0, 1; ld ra, 0(x); jr ra; addiu sp, sp, 0x10` — in C,
`void FUN_0034F3B8(void) { FUN_0011AAD0(1); }`. The boot gate accepted it **first try,
zero different bytes**, and the tutorial overlay rebuild matched with the same body placed
in it.

## Why a call body could not be placed before

A `jal` operand is an **absolute address**. Every other byte of a reviewed body is identical
wherever the body sits, which is what made the byte search of the earlier lots work; the call
target is not, so `finditer` of the boot bytes never matches the overlay's copy, and the
level link had no way to name the callee.

The measurement that opens the family, on the thirty-four call-citing targets already
identified:

1. mask the **26 target bits** of every `jal` in the body, keep the opcode;
2. search each overlay's `.text` for that masked pattern.

Result: **864 couples (32 bodies × 27 levels), each found exactly once, and every one of
them differs from the boot body ONLY in the call operands — zero other difference.** The
masked search is therefore not a heuristic: the bytes prove the placement, and the operand
the overlay carries gives the callee's **address in that level** for free.

## What the build had to learn

`scripts/integration.py` built every level catalogue with `"externals": {}`, stated as a
rule: *the reviewed level bodies are self-contained*. A level catalogue may now carry
`externals`, the same `name -> address` map the boot catalogue already had, and
`add_definitions` writes it into the linker script. The addresses are per level, because the
masked search measures them per level.

**The engine sits at fixed addresses.** For this first body the callee is the same
`0x0011AAD0` in the boot and in all twenty-seven overlays — the overlay calls below its own
`.text`, into the engine loaded once. A body calling a *level-local* function would instead
carry a different address per level, which the same per-level map expresses.

Two guards had to be taught the mask before the catalogue would accept the placement: the
level map's byte search **does** find these bodies, but its "the level bytes at the measured
address differ from the reviewed boot body" check compared all bytes exactly. It now compares
through the same mask, and the mask is all ones when a body has no `jal`, so every earlier
placement is checked exactly as before.

## A frozen catalogue entry, and 948 bytes it hid

Regenerating the catalogue turned up something unrelated and larger than the lot itself.
The tutorial's entry was **frozen at fifteen placements** while every other level carried
eighty: the generator preserved it (`levels = {TUTORIAL: document["levels"][TUTORIAL]}`),
by design, because the tutorial is built by a separate invocation.

With the tutorial regenerated by the same rule as the others it carries **eighty-one
placements**, and the tutorial build matches: **+66 placements, +948 bytes** that the
published total never counted. The tutorial's overlay is the same pinned file
(`c486f497…`) the other checks use, and its own gate confirms the bytes.

## Numbers, all measured

- boot gate: **94/94 matched, zero different bytes** (`check_candidates.py`);
- 27 overlays rebuilt, each with `matched: true` on its full `.text` and on the boot;
- **157 tests pass**; four expectations moved with the data (2 028 → 2 056, 93 → 94,
  269 → 270, tutorial 900 → 1 848 bytes and +15 → +81 units), and three tests that created a
  "wrong size" by writing the literal `8` now derive it from the real size — the tutorial's
  first placement is an eight-byte body, which made the literal silently correct;
- the CI export command reproduces `matched_code 51888` locally.

## What this changes for the remaining families

The reachable list recorded in the fifth lot was: 34 bodies citing a call (4 944 bytes),
19 citing a global (1 436), 15 VU/MMI, 5 `$gp`, 6 that read a temporary register before
writing it, and 76 plain bodies. **The call family is now open and pays twenty-seven times**;
the thirty-one remaining call bodies go through the same masked search and the same
`externals` map, one qualification each.
